# 动态行程执行、附近决策与复盘设计

| 项目 | 内容 |
| --- | --- |
| 日期 | 2026-08-17 |
| 状态 | Approved by Claude product review |
| 本轮范围 | 本地事件日志、快速调整、实际完成、附近决策降级、确定性复盘 |
| 后续范围 | Supabase 同步、高德实时 POI、商业平台合作数据、AI 自然语言分析 |

## 1. 问题与目标

现实行程不是静态清单。游玩超时、交通延误、临时取消和新想法会让后续安排连续变化。当前页面只能修改单个事件字段，修改只存在 React 内存，不能可靠表达跨天移动、整段顺延、交换、取消与实际完成，也无法保留“原计划为什么变成现在这样”的证据。

本设计先建立一个可追溯的本地执行层：原始计划永久作为比较基线，用户的每次操作写入事件日志，当前行程由基线和日志计算得到。这样既能立刻提升行中操作效率，也能让后续云同步和 AI 复盘复用同一数据模型。

成功标准：

1. 常见调整最多经过一次菜单选择和一次必要参数确认。
2. 刷新页面后修改仍在，同一行程不会与其他行程串数据。
3. 初始计划不被覆盖，任何当前状态都能追溯到具体变更。
4. 实际完成独立于计划状态，复盘只陈述有数据支持的事实。
5. 没有第三方数据授权时，不展示伪造评分、价格或“综合推荐”。

## 2. 方案比较与裁决

### 方案 A：本地事件日志先行（采用）

保存不可变初始快照和 append-only 变更日志，实时折叠得到当前行程。优点是本轮即可交付，并能自然迁移到 Supabase；缺点是暂时不能跨设备同步。

### 方案 B：先完成全部云协作

先实施 Supabase Auth、RLS、Realtime 和 mutation repository，再开发行程执行能力。最终一致性最好，但会把用户最急需的现场操作继续推迟，并引入部署与账户配置前置条件。

### 方案 C：AI 自然语言直接改行程

让用户输入“把黄崖洞移到明天，后面顺延一小时”。操作表面最少，但底层没有稳定 mutation 语义时，模型输出难以验证、撤销和审计。

裁决：以 A 为主线；A 的操作模型稳定后再接 B，最后让 C 只负责把自然语言解析为受约束的 mutation，不允许模型直接改任意 JSON。

## 3. 数据模型

浏览器存储键：`travelflow:execution:${tripId}`。

```ts
type TripExecutionPayloadV1 = {
  version: 1;
  initialSnapshot: TripWithDaysAndEvents;
  changes: TripChange[];
  updatedAt: string;
};

type TripChange = {
  id: string;
  tripId: string;
  type: 'update' | 'cancel' | 'move' | 'postpone' | 'swap' | 'actual-complete' | 'undo';
  eventId: string;
  createdAt: string;
  payload: Record<string, unknown>;
  undoOf?: string;
};
```

- `initialSnapshot`：第一次打开该 trip 时深拷贝保存，之后只读。
- `changes`：只追加，不原地修改或删除。撤销也是一条引用原 change id 的新记录。
- `currentTrip`：每次由 `initialSnapshot + active changes` 计算，不作为第二份事实源保存。
- 存储损坏时回退到传入的 trip，显示非阻断提示；不得用空数据覆盖损坏原值。
- 每条 change 带 `tripId`，折叠时再次校验，防止跨行程污染。

本地版本不提供“永久删除”。用户操作统一叫“标记取消”，卡片灰显并保留在“已取消”区域；界面明确说明“取消会保留在变更记录中，用于撤销和旅行复盘”。云端 owner 物理删除仍按既有协作设计单独实现。

## 4. 快速调整规则

每张行程卡提供显式“快速调整”菜单，不依赖长按、滑动或拖拽：

- `推迟 30 分钟`：当前项及同一天时间不早于当前项的后续项目整体平移 30 分钟；不自动跨到下一天。超过 23:59 的项目保留日期并清空不合法时间，显示“需重新安排时间”。
- `移到明天`：移动到下一天末尾，默认保留原开始/结束时间。最后一天没有“明天”时禁用。
- `选择日期`：在现有 trip days 中选择目标日，移动到目标日末尾。
- `与下一项交换`：交换两个事件的 dayId、开始时间、结束时间和排序位置；事件自身内容、时长与实际完成记录不交换。
- `标记取消`：写 cancel change，时间线灰显，不从历史消失。
- `标记实际完成`：记录用户点击时刻 `actualAt`，可撤销；不自动申请定位。

移动和交换后重新按当前时间排序，并检查受影响日期中的全部相邻事件；若出现时间重叠，界面给出派生警告，不把警告写进日志，也不擅自压缩游玩时长。所有操作完成后显示最近一次变更及“撤销”按钮；撤销写 undo change，保留审计链。连续点击撤销会依次撤销更早的有效业务变更，不提供 redo。

## 5. 附近决策助手

本轮不抓取美团、大众点评或携程网页，也不声称获得这些平台的评分和价格。

第一版提供两个可靠能力：

1. 用户主动点击“使用当前位置”后调用浏览器 Geolocation。坐标和基于坐标生成的临时候选顺序只在内存中使用，不写日志，也不进入计划与实际复盘；拒绝授权时继续使用当前行程点位。
2. 对当前计划内尚未完成、未取消且有坐标的事件计算直线距离，展示“行程内附近备选”。这是候选排序，不是实时营业或口碑推荐。

同时生成一个上下文完整的推荐问题，包含当前位置或当前景点、可用时长、同行构成、剩余计划及需要核验的平台维度。用户可以一键复制或调用系统分享面板发给豆包等已安装应用。文案明确要求外部助手返回来源、更新时间和可核验链接。

真实新增 POI 的后续实现采用高德 Web 服务周边搜索；餐厅/酒店的美团、点评、携程评分与实时价格只有在取得正式合作权限后才进入排序。没有授权时只能提供平台跳转/检索上下文，不能做“多平台综合评分”。

## 6. 计划与实际复盘

第一版使用确定性计算，不调用模型：

- 初始计划项数、当前有效项数、取消项数；
- 更新、移动、顺延、交换次数；
- 已标记实际完成项及未完成项；
- 有计划时间的事件与 `actualAt` 的时间偏差；
- 按天列出“原计划 → 当前安排 → 实际状态”。

报告只从快照和 change log 得出事实，不推断“为什么延误”或“这个安排不好”。页面提供“复制给 AI 深度分析”，把结构化事实、旅行偏好和明确问题组合为提示词。后续模型接入必须返回：观察、证据、可能原因（标为推测）、下次可执行规则；不得把推测写回事实字段。

## 7. 云端与第三方落地边界

本轮直接实现：

- 本地事件日志与安全解析；
- 取消、移动、顺延、交换、撤销、实际完成；
- 行程内附近备选与推荐问题复制；
- 确定性复盘与 AI 分析上下文导出。

后续方案：

- Supabase：复用现有 Anonymous Auth、viewer/editor token、RLS 与 Realtime 方案，把 changes 作为可同步 mutation/event 表；生产设置与部署必须另行验收。
- 高德：申请 Web 服务 API Key 后，由服务端 Route Handler 调用周边搜索，Key 不下发浏览器；缓存短时 POI 结果并标注来源时间。
- 美团/点评/携程：需要企业/合作伙伴申请与商务审批。审批前不抓取页面、不反向工程私有接口。
- AI：沿用现有 OpenAI-compatible 服务端入口，让模型读取结构化复盘，不让模型绕过 mutation 校验直接写行程。

## 8. 错误处理与隐私

- localStorage 不可用：保留本次内存操作并提示“刷新后可能丢失”。
- 变更引用不存在的 event：忽略该 change，记录为解析警告，不让页面崩溃。
- 定位拒绝/超时：使用当前事件或用户选择地点作为上下文，不重复弹权限。
- 时间顺延溢出：标记需重新安排，禁止产生非法 `24:xx`。
- 外部推荐无来源：不进入正式推荐卡，只能作为待核验候选。
- 定位坐标和临时候选排序默认不持久化，也不要求可回放；未来若记录实际轨迹，必须单独取得同意并提供清除入口。

## 9. 验收场景

1. 黄崖洞从今天移到明天，刷新后仍在明天；初始快照仍显示原日期。
2. 当前项目推迟 30 分钟，同日后续项目同步顺延，其他日期不变。
3. 任意两项交换后内容不串、各自时长不变；重叠时出现警告。
4. 取消项目后卡片灰显并说明数据仍保留；撤销后恢复。
5. 标记实际完成后复盘计数增加；撤销后恢复，日志仍能看到两次操作。
6. 两个不同 trip 的本地变更互不影响，损坏 payload 不覆盖原计划。
7. 拒绝定位时页面正常工作；同意后只对已有地理点按距离排序。
8. 未配置第三方服务时不出现虚构评分、价格或“来自美团/携程”的断言。
9. 复盘报告中的每项数字都能由 snapshot 或 change log 重算。
