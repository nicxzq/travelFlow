## 1. 目标与范围

让每个注册用户在 `travel.carlxu.cn` 上创建、保存、修改和跨设备查看**属于自己的**行程。

一期范围：

1. 邮箱 + 密码注册登录，会话经由 cookie 在服务端可信读取。
2. 全部业务表启用 Row Level Security，用户只能读写自己的行程。
3. 行程写入原子化：一份行程的 trip / days / events 要么全部落库，要么全部不落。
4. 两条静态 seed 行程入库为**全站可读、不可写**的示例模板，用户可一键复制为自己的行程。
5. 浏览器 localStorage 中的既有生成记录可在登录后幂等导入。
6. 手机号以「登录后在设置页绑定」的形式接入，不作为一期注册入口（理由见 §5.3）。

### 1.1 架构定位

| 组件 | 归属 | 说明 |
| --- | --- | --- |
| Next.js 应用 | 自管 Linux 服务器 | 唯一部署物，PM2 / systemd 托管 |
| Auth / Postgres / Storage | Supabase 托管 | 不自建数据库 |
| 短信投递 | 阿里云或腾讯云 | 经 Supabase Send SMS Hook 回调本站接口 |

## 3. 关键决策

每条含被否决方案，避免后续重复讨论。

| # | 决策 | 否决项与理由 |
| --- | --- | --- |
| D1 | 服务端会话用 `@supabase/ssr`，每请求新建 client | 沿用浏览器单例：Node 无 `localStorage`，JWT 为空，RLS 判否后**返回空数组而不报错**；且常驻进程中单例跨请求共享，存在跨用户串号 |
| D2 | 服务端一律 `getUser()`，禁用 `getSession()` | `getSession()` 只反序列化客户端可控的 cookie，不构成授权依据 |
| D3 | **客户端不直连 Supabase**，全部 CRUD 走 Server Action | 浏览器直连使每个用户各自产生跨境链路，不可测不可控；集中到服务器后只剩一条链路 |
| D4 | 模板用 `user_id IS NULL` + `is_template` + CHECK 约束 | 建系统幽灵账号：需保证无人能登录，额外攻击面。且 NULL 使 owner 谓词自然求值为非真，无需额外条件 |
| D5 | 业务 RPC 用 `security invoker` | `security definer`：绕过 RLS，一旦函数内校验有疏漏即为越权通道。invoker 让 RLS 成为第二道网。definer 仅用于 `handle_new_user`（必须写 profiles） |
| D6 | 坐标改用 `lat` / `lng` 双精度列 | 沿用 PostGIS：`st_makepoint(x, y)` **经度在前**而全项目 domain 是 `{lat, lng}`，翻转事故概率高；`search_path=''` 下需全限定 `extensions.*`；PostgREST 返回 WKB hex 前端还要解析；而 `lib/domain/journey.ts` 只做直线连点，零空间查询 |
| D7 | AI 原文存独立表 `trip_documents` | 存 `trips` 的 jsonb 列：单份 30–80KB，`.select('*')` 一失手即把 N 份 payload 拖过跨境链路 |
| D8 | 一期注册入口只有邮箱 | 见 §5.3 |
| D9 | seed 用 `slug` 列 + slug-first 路由查找 | 改 `trips.id` 为 text：污染整个 schema；改 URL 为 UUID：现有链接失效且不可读 |

## 4. 会话架构

### 4.1 为什么现有单例不可用

`lib/supabase/client.ts:33-35` 在模块顶层创建单例。三层问题，由轻到重：

1. **拿不到会话**。`supabase-js` 默认 auth storage 是 `localStorage`；Node 中退化为进程内存。服务端查询以 `anon` 角色执行，启用 RLS 后 owner 策略判否，**返回空数组而非异常**——表现为「登录了却一条行程都没有」，没有任何可 catch 的错误。这是最难定位的一类故障。
2. **当前即是未授权通道**。五表无 RLS，而 anon key 随 `NEXT_PUBLIC_` 进入浏览器包。任何人都能对 `trips`/`days`/`events`/`memories` 做 CRUD。目前无数据故无损失，**但 RLS 必须先于任何真实数据写入**。
3. **常驻进程中的跨用户污染**。`next start` 是长驻进程，模块单例生命周期等于服务器生命周期。若在服务端对该单例调用 `setSession()`，用户 A 的 JWT 会污染并发请求中用户 B 的查询。低并发测试环境完全测不出来。

### 4.2 文件划分

| 文件 | 职责 |
| --- | --- |
| `lib/supabase/client.ts` | 重写为 `createBrowserClient`；**必须保留 `createSupabaseBrowserClient` 导出名**（`validate-scaffold.mjs:93` 断言该字符串） |
| `lib/supabase/server.ts` | `createSupabaseServerClient()`，读 `next/headers` 的 `cookies()`。**每次调用新建，禁止模块级缓存** |
| `lib/supabase/middleware.ts` | `updateSession(request)` |
| `middleware.ts` | 根中间件 + matcher |
| `lib/supabase/admin.ts` | 首行 `import 'server-only'`；service_role client；`persistSession: false` |
| `lib/auth/current-user.ts` | `React.cache` 包裹的 `getUser()`，单请求内去重 |
| `app/actions/auth-actions.ts` | 注册 / 登录 / 登出 / 发码 / 验码 |

### 4.3 版本与写法约束

本项目为 **Next.js 14.2.30**，与 Supabase 官方文档当前示例存在三处差异，照抄会直接失败：

| 官方示例（Next 15/16） | 本项目（Next 14） |
| --- | --- |
| `const cookieStore = await cookies()` | `const cookieStore = cookies()`（同步） |
| 入口文件 `proxy.ts` / `export function proxy` | `middleware.ts` / `export function middleware` |
| `supabase.auth.getClaims()` | `supabase.auth.getUser()` |

`@supabase/ssr` 必须 **≥ 0.5.0**：0.5 起 cookie 接口由 `{ get, set, remove }` 改为 `{ getAll, setAll }`，用错接口的症状是「登录成功但一刷新就登出」。已装 `@supabase/supabase-js` 为 2.95.3。

### 4.4 两个必须照抄的样板

**Server Component 中 `cookies().set()` 会抛异常，吞掉它是官方模式**，前提是 middleware 承担刷新。二者缺一：只有 catch 没有 middleware，token 过期后永远刷不新；只有 middleware 没有 catch，Server Component 渲染直接 500。

**middleware 中重定向必须复制 cookie**：

```ts
const redirect = NextResponse.redirect(new URL('/login', request.url));
response.cookies.getAll().forEach((c) => redirect.cookies.set(c));
return redirect;
```

漏掉这段，刷新后的新 token 丢失 → 浏览器继续带旧 token → 再刷新 → 再丢失 → **无限登出循环**。且只在 token 过期（默认 1 小时）后复现，本地开发几乎测不到。

在 `createServerClient` 与 `getUser()` 之间**不得插入任何代码**，尤其是其他 `await`。

### 4.5 AI 流式路由的特殊约束

`app/api/ai/generate/route.ts` 返回 `ReadableStream`。**响应头一旦发出就无法再写 `Set-Cookie`**。因此该路由只读身份、不触发 token 刷新（刷新交给 middleware，matcher 需覆盖 `/api/ai/:path*`）；未登录时必须**在开流之前**返回 401 JSON。

## 5. 认证渠道

### 5.1 邮箱 + 密码（一期）

Supabase 原生支持，开启 Confirm email。确认链接落 `app/auth/confirm/route.ts`，走 `verifyOtp({ token_hash, type })`。

### 5.2 手机号 + 短信 OTP 的链路设计

```
浏览器 → Server Action → 本站服务器 → supabase.auth.signInWithOtp({ phone })
                                          ↓ Supabase 触发 Send SMS Hook
                            HTTP POST → https://travel.carlxu.cn/api/auth/hooks/send-sms
                                          ↓ 本站服务器
                                    阿里云短信 API → 用户手机
浏览器 → Server Action → supabase.auth.verifyOtp({ phone, token, type }) → 签发 session
```

选择 Send SMS Hook 而非自管 OTP 的理由：只替换**投递通道**，OTP 的生成、哈希存储、有效期、一次性消费、失败计数，以及**最难自己做对的「签发合法 session」**全部仍由 Supabase Auth 负责，我们不碰任何密码学。

被否决的自管 OTP 方案：`supabase-js` v2 的 Admin API 没有「为任意用户创建 session」的接口。可行绕法（`generateLink` 造影子邮箱、或临时改密码后 `signInWithPassword` 再轮换）都把自造认证轮子的风险引进来，收益仅是省掉跨境 Hook，不值得。

内置 Provider（Twilio / MessageBird / Vonage / TextLocal）对 +86 不可用：国际短信需运营商侧预先报备签名模板，未报备者在网关被**静默丢弃**（不是慢，是无回执地消失）；成本为国内短信的 10–30 倍；显示为境外号码，普遍被安全软件标记。

### 5.3 为什么一期不做手机注册入口

手机注册串联了 4 个团队不可控的外部依赖：

1. Send SMS Hook 的 plan tier 要求（待确认，§12）
2. `carlxu.cn` 的 ICP 备案
3. 阿里云短信签名与模板审批（可能被驳回，个人主体资质受限）
4. **跨境入站** Hook 的可达性——方向与本站出境相反，通常更差，且位于登录关键路径

任一环卡住都会阻塞交付，而云端持久化主线（§6–§9）与登录渠道**完全解耦**。

一期做法：手机号走「已登录 → 设置页 → 绑定」，即 `auth.updateUser({ phone })` + `auth.verifyOtp({ type: 'phone_change' })`。此时短信失败只是「绑定失败，稍后重试」，而非「新用户注册不进来」，风险等级完全不同。绑定链路在小流量下连续 7 天成功率 > 98% 后，再把手机开放为注册入口，前端改动仅为多一个 tab。

### 5.4 Hook 端点的安全要求

| 要求 | 后果 |
| --- | --- |
| 用 `standardwebhooks` 验签（`v1,whsec_...`） | **漏掉即成短信轰炸机**，任何人 POST 该端点就能让你发短信直到欠费 |
| 端点必须 < 1s 返回 | 验签 → 调用阿里云 → 立即 200。不得在 Hook 内做 DB 查询或重试循环 |
| 阿里云调用设 800ms 超时 | 失败即返回非 200，前端提示「发送失败请重试」，而不是让用户干等 |

### 5.5 限流

Supabase 自带的 SMS rate limit 不作为唯一防线——超额代价是真金白银。在发码 Server Action 与 Hook 端点各加一层：

- 同手机号：60 秒冷却 / 10 分钟 ≤ 3 条 / 24 小时 ≤ 8 条
- 同 IP：24 小时 ≤ 20 条；同 /24 网段 ≤ 100 条
- 第 2 次发码起强制人机校验。**注意 Supabase 内置 CAPTCHA 只支持 hCaptcha 与 Cloudflare Turnstile，二者在大陆可达性同样存疑**，故人机校验放在本站 Server Action 层接阿里云验证码 2.0，不使用 Supabase 内置配置
- 计数器落 `otp_rate_limits(key text primary key, window_start timestamptz, count int)` + `security definer` 原子自增函数。本阶段无 Redis，一次跨境往返（~200ms）在发短信场景可接受

## 6. 身份模型

### 6.1 profiles 行的创建

**触发器为主，应用侧幂等兜底为辅。**

不能只靠应用代码：用户可经邮件确认、OAuth 回调、Admin API 等多条路径首次落地，每条都记得调用是不现实的；漏一条即产生「有 `auth.users` 无 `profiles`」的孤儿，而 `trips.user_id` 外键指向 `profiles(id)`，孤儿用户建行程直接 **23503 外键违约**，错误对用户毫无意义。

不能只靠触发器：上线前的存量用户没有 profile，且触发器失败时需要自愈路径。

### 6.2 触发器的四项强制要求

| 要求 | 理由 |
| --- | --- |
| `security definer` | 普通角色无权写 `public.profiles` |
| `set search_path = ''` + 全限定名 | **提权攻击的直接防线**。不设则 `search_path` 继承调用者，攻击者可建同名 `profiles` 表让 definer 函数以 postgres 权限操作其控制的对象。设空后漏写 schema 会立即报错——正是想要的失败模式 |
| `on conflict (id) do nothing` | Supabase 对 `auth.users` 的写入在 confirm、identity link 等流程中可能重放 |
| `exception when others then return new` | **最重要一条**。触发器与 `auth.users` 的 INSERT 同事务，抛异常即回滚整个注册，用户看到 `Database error saving new user` 这一无法排查的黑盒错误。加 exception 块后 profile 插入回滚到 savepoint 但注册成功，随后由应用侧补齐 |

另需 `revoke execute ... from public, anon`：Postgres 对新函数默认授予 `PUBLIC` 角色 EXECUTE。（触发器函数的 EXECUTE 权限只在 `CREATE TRIGGER` 时检查，触发时不做 ACL 检查，故 revoke 不影响触发；owner 保留自身权限，建触发器照常成功。）

**兜底通道必须真实存在。** `profiles` 只有 SELECT / UPDATE 策略、无 INSERT 策略——这对触发器是安全且正确的（definer 以表 owner `postgres` 身份运行，表未设 `FORCE ROW LEVEL SECURITY`，owner 不受 RLS 约束）。但这意味着应用侧**没有任何 INSERT 权限**。若触发器被 exception 块吞掉失败，用户就永久卡在「有 `auth.users` 无 `profiles`」状态：建行程时 `trips.user_id` 外键报 23503，且该错误不是 `unique_violation`、不被业务 RPC 的处理器接住，原始 Postgres 错误直接冒到用户面前。

因此必须提供一个**只能写调用者自己那行**的 definer 函数 `ensure_profile()`（无参数，内部从 `auth.uid()` 取 id），由 Server Action 入口调用。这与「不在业务 RPC 内 upsert」并不矛盾——它是独立函数，不是 invoker RPC 内部的越权写入。

### 6.3 竞态

| 竞态 | 后果 | 处置 |
| --- | --- | --- |
| 触发器与应用侧兜底并发插入同一 id | 23505 | 两侧均 `on conflict do nothing`，应用侧把 23505 视为成功 |
| 注册后立即并发建行程，profile 未落地 | 23503 | 应用侧 `ensureProfile()` 在 Server Action 入口调用一次。因 D5 采用 invoker RPC，业务 RPC 内不做 upsert（无权写 profiles）；兜底改由**独立的 `ensure_profile()` definer 函数**承担，见下 |
| 同手机号并发注册 | `auth.users.phone` 唯一约束 | Supabase 自身处理，前端正确展示错误 |

### 6.4 避免同一人产生两个账号

`auth.users` 一行同时有 `email` 与 `phone` 两列，各自唯一——「一人一账号双通道登录」在数据模型上原生支持。**但 Supabase 不会自动合并**：邮箱注册后再用 `signInWithOtp({ phone })`，Supabase 找不到该 phone 就**新建一个 user**，于是同一人有两个账号两套行程。

一期策略：

1. 注册入口只有邮箱（§5.3）。
2. 手机号只能从**已登录状态**绑定，走 `phone_change` 流程，写进已有 user 行，不产生新身份。
3. 手机号已被他人占用时 Supabase 报唯一约束错误 → 前端文案「该手机号已绑定其他账号」，**不做自动合并**。
4. **一期明确不做账号合并**。合并意味着把 A 的所有 trips 及级联子表改挂到 B 再删 A，不可逆且有数据丢失风险，需专门的确认流程、审计日志与回滚预案。列入后续 backlog。

### 6.5 profiles 的定位

`profiles.email` 会与 `auth.users.email` 漂移。定位为**展示用快照，非权威**：仅由 INSERT 触发器写一次，用户在设置页改资料时由应用同步。权威来源永远是 `auth.users`。新增 `phone` 列。

**铁律：绝不用 `raw_user_meta_data` / `user_metadata` 做任何授权判断**——它可由用户经 `auth.updateUser({ data })` 任意修改。权限只能来自 `trips.user_id` 或 `app_metadata`（后者仅服务端可改）。

## 7. 数据模型与 RLS

### 7.1 seed 主键冲突的处置

`trips.id` 是 uuid，而 `/trip/shanxi-loop-2026` 这个 URL 已存在于 `trip-library.tsx:59,90`。

处置：新增 `trips.slug text` 唯一列，路由**先按 slug 查，查不到再按 uuid 查**。模板保留原字符串作 slug，内部使用真实 uuid；用户复制出的行程无 slug，只用 uuid。

同理，seed 的 **event id** 存入 `events.legacy_key`，唯一索引 `(trip_id, legacy_key)`（跨行程不冲突）。**day id 不入库**——`days` 表不设 `legacy_key`，seed 脚本仅用 day id 在内存中给 event 归组，落库时按 `day_index` 对齐。这使 §9.3 的 overlay 迁移从「需要复杂 id 映射」降级为「一次 key 查表」——`lib/mock/shanxi-actual.ts:278` 已导出 `shanxiActualOverlay`，正是要迁移的数据。

`days` 另需 `(trip_id, day_index)` 唯一约束：模板复制与 AI 导入都按 `day_index` 对齐，重复值会导致 event 错挂。

### 7.2 新增与变更

```
profiles      + phone, updated_at
trips         + slug, is_template, template_source_id, client_import_key, cover_url, updated_at
              ~ user_id 去掉 NOT NULL
              + CHECK (is_template ⊻ user_id 存在)
days          + theme, updated_at
events        + lat, lng, transport_mode, legacy_key, image_url, story, tags
trip_documents  新表：trip_id PK, schema_version, source_prompt, payload jsonb
otp_rate_limits 新表：key PK, window_start, count
ai_usage_quotas 新表：user_id + day PK, count
```

索引补齐：`trips(user_id)`、`trips(slug) unique where not null`、`trips(user_id, client_import_key) unique where not null`、`trips(is_template) where is_template`、`days(trip_id)`、`events(trip_id)`、`events(day_id)`、`events(trip_id, legacy_key) unique where not null`、`memories(trip_id)`、`memories(event_id)`。

**`db/schema.sql` 全文无一条 `create index`**，而 RLS 策略全部过滤 `trip_id`——缺索引会让每次策略检查退化为 seq scan。

### 7.3 RLS 策略要点

`profiles`：只读写自己，**不给 INSERT / DELETE 策略**（只允许触发器以 definer 身份写入）。

`trips`：**逐命令写策略，不用 `FOR ALL`**。原因见 §7.4。SELECT 对 `anon, authenticated` 开放 `is_template = true or user_id = (select auth.uid())`；INSERT / UPDATE / DELETE 均带 `user_id = (select auth.uid()) and is_template = false`。

`days` / `events` / `trip_documents`：通过两个 `language sql` + `stable` + `security invoker` 的辅助函数收敛谓词——`is_trip_readable(trip_id)`（含模板）用于 SELECT，`is_trip_owner(trip_id)`（排除模板）用于写。

**关于内联的事实订正**：`set search_path = ''` 会写入 `pg_proc.proconfig`，而 `inline_function()` 对 `proconfig` 非空的函数直接否决内联。因此这两个函数**不会被内联，谓词按行调用**。此处以安全性优先接受该成本（谓词只做 `trips` 主键查找，代价可控）。若要兼得内联与安全，可改用 PG14+ 的标准函数体 `begin atomic ... end`——它在创建时完成解析并记录依赖，天然免疫 search_path 劫持，且不写 `proconfig`。

**这两个辅助函数必须保留 `PUBLIC` 的默认 EXECUTE 授权**，与 §8.3 的 RPC 规则相反。它们被 `to anon` 的 SELECT 策略调用，一旦 revoke，anon 访问模板页会直接报错。

`events` 的 INSERT / UPDATE `WITH CHECK` **必须额外校验 `day_id` 归属**：

```sql
and exists (select 1 from public.days d where d.id = day_id and d.trip_id = events.trip_id)
```

否则用户可把自己的 event 挂到他人的 day 上——`day_id` 不受 `trip_id` 谓词保护。

`memories`：仅 owner 可读写，模板不开放。

### 7.4 USING 与 WITH CHECK

- `USING` 决定**哪些既有行可见 / 可命中**，作用于 SELECT / UPDATE / DELETE。
- `WITH CHECK` 决定**写入后的行必须满足什么**，作用于 INSERT / UPDATE。

UPDATE 两者都要。只写 `USING` 的后果非常具体：

```sql
update trips set user_id = '<他人 uuid>' where id = '<我的 trip>';   -- 行被送给别人
update trips set is_template = true where id = '<我的 trip>';        -- 私人行程变全站可读
```

`USING` 校验「改之前是我的」全部通过。故 trips 的 UPDATE `WITH CHECK` 里必须同时钉死 `user_id` 和 `is_template = false`。`FOR ALL` 会让这层区别隐形，所以 trips 与 events 坚持逐命令写。

### 7.5 性能

`(select auth.uid())` 而非裸 `auth.uid()`：包一层子查询后 Postgres 将其作为 **InitPlan 整条语句只求值一次**；裸调用被当作 volatile 表达式**逐行求值**。`db/itinerary-management-extension.sql:56` 已是此写法，保持一致。

### 7.6 坐标列（D6 详述）

新增 `events.lat` / `events.lng` 为**唯一真值来源**；`geo_point` 保留但不写不读，标记 deprecated。理由已在 D6 列出，核心是 `st_makepoint` 的参数顺序与项目 domain 相反，一旦写反地图上所有点会跑到另一个半球，而应用侧（`lib/domain/journey.ts` 的 `buildJourneySegments`）只需直线连点，无任何空间查询需求。未来确需「附近的景点」时再回填。

### 7.7 模板只读是如何成立的

- `is_template = true` 的行对 anon 与 authenticated 均可 SELECT → 未登录也能浏览示例
- INSERT / UPDATE / DELETE 策略全部带 `is_template = false` → **无任何普通角色能写模板行**
- 子表经 `is_trip_readable` 可读、`is_trip_owner` 不可写
- 模板写入只能由 service_role（迁移脚本）完成

## 8. 持久化映射与原子写入

### 8.1 双表示，单向投影

`GeneratedItinerary` 中 `overview` / `transportation` / `accommodationDining` / `practicalInfo` 共 13 个字符串数组，**没有任何表能装**。为它们建 5 张新表是本阶段最典型的过度设计。

| | `trip_documents.payload` | `trips` / `days` / `events` |
| --- | --- | --- |
| 内容 | 逐字保存 AI 产出的 `GeneratedItinerary` | 交互态：时间、状态、完成勾选、todo、地图点、overlay |
| 可变性 | 创建时写一次；重新生成时整体替换并递增 `schema_version` | 用户每次编辑都写 |
| 谁读 | 概览页的交通汇总 / 住宿餐饮 / 实用信息等纯展示区块 | 时间轴、当日导引、journey 地图、todo |

**投影是单向的，且只在创建时发生一次。绝不做双向同步。** 用户改了 event 时间后再读 payload 里的 `detailedItinerary[].events[].time`，两边不一致是必然的。

**规则：payload 中只渲染规范化表里不存在的字段。`detailedItinerary` 在投影完成后不再被任何 UI 读取。** 这条边界必须写进实施文档，否则半年后必然有人从 payload 里读时间。

### 8.2 原子写入

`supabase-js` 每次调用 = 一次 HTTP 请求 = 一个独立事务，**无客户端事务 API**。写一份 6 天行程需 trip + 6 day + 约 40 event = 47 次往返，跨境链路下约 10 秒，且中途失败会留下半截行程（有 trip 有 days 无 events），用户看到一个空壳，没有任何客户端补偿逻辑能可靠修复。

**唯一正确解：Postgres 函数经 `supabase.rpc()` 调用**，函数体运行在单一隐式事务中，任何 exception 全部回滚。一次往返，全有或全无。

三个函数：

| 函数 | 用途 |
| --- | --- |
| `create_trip_from_itinerary(payload, import_key, source_prompt)` | 创建 / 幂等导入 |
| `replace_trip_content(trip_id, payload)` | 重新生成后覆盖 |
| `copy_template_trip(source_id)` | 模板复制 |

### 8.3 RPC 的四条铁律

1. **绝不把 `user_id` 作为参数传入**，一律从 `(select auth.uid())` 内部取。传参即是越权注入点。
2. `security invoker`（D5）+ `set search_path = ''` + 全限定名。
3. `revoke execute from public, anon` + `grant execute to authenticated`。
4. **Zod 校验在 Server Action 层先做一遍**（`lib/validation/itinerary-schema.ts`）。SQL 里的 `left()` / `nullif()` / 长度上限是**第二道防线而非唯一防线**——`generate-form.tsx` 允许用户手改 JSON 后保存，payload 完全用户可控。

`copy_template_trip` 有一条独立的关键校验：

```sql
if not exists (select 1 from public.trips where id = p_source and is_template) then
  raise exception 'not a template' using errcode = '42501';
end if;
```

漏掉这句，任何登录用户都能把**任意 trip_id** 复制成自己的——一个完整的越权读取通道。

同时函数内需设硬上限（payload ≤ 512KB、`detailedItinerary` ≤ 30 天），防止误操作或 DoS。注意 `pg_column_size()` 测的是 jsonb 二进制表示，与 JSON 文本长度不等价，仅作粗略护栏。

### 8.4 铁律五：invoker RPC 内禁用 data-modifying CTE

**只要目标表的 RLS 谓词需要读另一张在同一条语句内被写入的表，就不能用 data-modifying CTE，必须拆成 plpgsql 循环。**

原因是 Postgres 的快照语义：CTE 与主查询共享同一 snapshot 和同一 CommandId，`HeapTupleSatisfiesMVCC` 判定 `cmin >= snapshot->curcid` 即不可见。主查询能拿到 CTE 的 `RETURNING` 结果，是因为那些行落在 tuplestore 里由 CteScan 读取；而 RLS 谓词里的 `exists (select 1 from ...)` 是 SubPlan，**要真去扫堆表**，走的正是不可见那条路径。两种机制不同，不能互相佐证。

具体到本项目：`events` 的 INSERT 策略含 `exists (select 1 from public.days ...)`，因此复制模板时 days 与 events **不能写在同一条语句里**。而 plpgsql 函数内的多条语句之间 SPI 会调用 `CommandCounterIncrement()`，后一条语句能看见前一条的效果——这正是 `create_trip_from_itinerary` 的循环写法成立、而 CTE 写法失败的唯一区别。

同理，外键检查走 AFTER ROW 触发器、在语句末尾计数器递增之后执行，**不会先于 RLS 报错**，所以这类缺陷的症状是 `42501 new row violates row-level security policy`，而非外键错误。

## 9. 导入与模板

### 9.1 数据源

| key | 位置 | 形态 |
| --- | --- | --- |
| `travelflow_local_itinerary_list_v1` | `generate-form.tsx:16` / `trip-library.tsx:15` | `Array<{ id, createdAt, sourcePrompt, itinerary }>`，上限 20 条（`generate-form.tsx:229`） |
| `travelflow_local_itinerary_v1` | 同上 | 单个 `GeneratedItinerary`，当前编辑草稿 |
| `travelflow:journey-overlay:{tripId}:v1` | `journey-store.ts:8` | `Record<eventId, { imageUrl, story, tags }>` |

关键区分：list 中的 `itinerary` 是 `GeneratedItinerary`，其内部**没有任何 event id**（`lib/domain/trip.ts:88-100`），而 overlay 按 event id 索引。但 overlay 只在 `/trip/[id]` 工作台产生，AI 生成结果只在 `/new` 展示——**AI 生成的行程根本没有对应 overlay**，导入时无需处理。overlay 迁移只发生在 seed 模板复制场景，且 seed 的 id 是确定性的，经 `legacy_key` 一次查表即可。

### 9.2 幂等

```
importKey = `local-v1:${sha256(`${item.id}|${item.createdAt}|${item.itinerary.tripTitle}`).slice(0, 32)}`
```

`item.id` 是 `Date.now()`（`generate-form.tsx:223`），单浏览器内稳定但非全局唯一，故拼上 createdAt 与标题。唯一索引 `(user_id, client_import_key)` 跨用户不冲突；同一份数据从两个浏览器导入同一账号只建一条。

### 9.3 流程要点

- **绝不自动导入**。必须用户显式勾选并点击确认。公用电脑上自动导入会把上一个人的行程导进当前账号。
- **串行而非并发**。并发放大 unique_violation 概率，而跨境链路上并发也快不了多少（每条 RPC 本身就是一次往返）。每条成功后立即落盘标记，中途关页面最多损失一次重复尝试（RPC 幂等，重试无害）。
- **绝不删除原始 localStorage 数据**，只写 `travelflow:import-state:v1` 标记。清理由用户点独立按钮显式触发。
- 因 RPC 对 `(user_id, import_key)` 幂等，**「全部重试」永远安全**，失败态无需精细补偿，一个重试按钮即可。这是幂等键设计的最大工程收益。

### 9.4 Overlay 的两条安全要求

1. **`isSafeImageUrl` 必须在服务端重跑**。`lib/journey/journey-store.ts:16-27` 是客户端实现；Server Action 是公开 HTTP 端点，客户端校验永远不是安全边界。抽到 `lib/journey/url-safety.ts` 供两端共用。
2. **拒绝 `data:` URL 入库**。overlay 当前允许 `data:image/...`（`journey-store.ts:20`），用户很可能塞了 base64 图片，单张可达数 MB，入 `events.image_url` 会撑爆行、拖慢每次查询、打满跨境流量。一期直接拒绝并提示「请改用图片链接，本地图片将在后续版本支持上传」——Storage 上传本就在下一阶段。

## 10. 风险登记册

### 10.1 三项主要风险

**R1 · Supabase 从中国大陆的可达性。** 这是唯一「做不成则整个方案作废」的风险，且不在任何代码里——所有设计都建立在「服务器能稳定访问 `*.supabase.co`」这个**未经验证的假设**上。必须在写第一行代码前用 24 小时探测数据证实或证伪。若不可接受，正确应对是改换数据库托管（国内云 Postgres + Logto / Casdoor 之类），而不是硬撑。

注意：Supabase 的 Custom Domain 付费加装件只是把 CNAME 指向其边缘节点，**不改善大陆可达性**，不要指望它。

**R2 · 手机 OTP 链路。** 四个串行外部依赖，见 §5.3。处置：已从一期关键路径移除。

**R3 · Cookie / Session 管道的静默故障。** 两个形态：(a) middleware 重定向时丢失刷新后的 cookie → 用户随机登出，只在 token 过期后复现；(b) 服务端误用 `getSession()` → 攻击者伪造 cookie 即可冒充任意用户，而**功能测试全部通过**。这类缺陷不会在 CI 里变红，只会在生产出事。处置：§4.4 两段样板不可改动；code review 检查项加一条「服务端出现 `getSession(` 即 block」。

### 10.2 其余失败模式

| 风险 | 表现 | 处置 |
| --- | --- | --- |
| 分享页 IDOR | 猜到 uuid 即可读他人行程 | 一期把 `/trip/[id]/share` 降级为 owner-only，等 `share_tokens` 落地再开放。**接库当天必须处理** |
| AI 路由被薅 | 无限调用烧 `OPENAI_API_KEY` | 加 `getUser()` 401 + `ai_usage_quotas` 每日上限。这是**当前的线上问题**，非未来风险 |
| **配额可被被计数者自行重置** | 用户拿浏览器里的 anon key + 自己的 JWT 直接 `PATCH /rest/v1/ai_usage_quotas` 把 count 改回 0 | **计数器绝不能对被计数的角色开放写权限**。`authenticated` 只给 SELECT，写入唯一通道是 `consume_ai_quota()` definer 函数 |
| 未登录访问 API 被重定向而非 401 | middleware 的 `NextResponse.redirect` 会让 `fetch` 跟随 307 拿到 HTML，路由内的 401 分支永不执行 | middleware 对 `/api/` 前缀返回 401 JSON，不重定向 |
| overlay 本地数据成孤儿 | seed 入库后 `trip.id` 由 slug 变为 uuid，而既有 overlay 存在 slug key 下，页面读空 key → 用户已有图片/游记直接消失 | overlay key 统一用 `slug ?? id`，并做一次性 key 迁移 |
| RLS 开了但 GRANT 没给 | PostgREST 返回 42501 | 迁移顺序：GRANT 先于 enable RLS |
| GRANT 给了但策略没写 | SELECT **返回空数组不报错**，前端表现为「数据丢了」 | 冒烟测试必须断言「能读到自己的行」，不能只断言「读不到别人的」 |
| `npm test` 变红 | `validate-scaffold.mjs:128` 断言 `generate-form.tsx` 含 `localStorage.setItem` | 改造该组件后需同步更新断言。注意 `:258/:263` 的 `Row Level Security` / `share_tokens` 断言目标是**旧文档** `Supabase同步设计文档.md`，只要不删除旧文档就仍然绿，与本文档无关 |
| middleware 不是安全边界 | Next 14 曾有 `x-middleware-subrequest` 绕过（CVE-2025-29927），当前 `^14.2.30` 已含修复（14.2.25+） | 授权最终依据永远是 RLS + Server Action 内的 `getUser()`，middleware 只做重定向体验 |
| service_role 泄漏 | 全库无 RLS 访问 | `lib/supabase/admin.ts` 首行 `import 'server-only'`；env 名不带 `NEXT_PUBLIC_` |
| HTTPS 缺失 | auth cookie 需 `Secure`，HTTP 下浏览器不存 → 登录后立刻掉线 | 服务器必须配好 TLS，Next 需感知 `X-Forwarded-Proto` |
| 部署产物过大 | `next.config.mjs` 无 `output: 'standalone'` | 自管 Linux 建议加 standalone + PM2 / systemd |
